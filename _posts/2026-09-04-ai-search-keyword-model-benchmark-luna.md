최근 한국어 **검색 키워드 생성**처럼 비교적 좁고 명확한 태스크에서 여러 LLM을 비교해볼 일이 있었다.

처음에는 당연히 비싼 모델일수록 결과도 안정적으로 좋을 거라고 생각했다.

그런데 실제로 2,000건을 같은 조건에서 돌려보니 꽤 의외의 결과가 나왔다.

**GPT-5.6 Luna의 오탐률이 Opus 5와 사실상 구별하기 어려운 수준까지 내려왔고, 비용은 훨씬 낮았다.**

물론 여기서 바로 "Luna가 Opus보다 좋은 모델이다"라고 결론내리면 안 된다.

이번 비교는 어디까지나 **검색 키워드 생성이라는 좁은 태스크**에서의 결과다.

오히려 재미있었던 건 세 가지였다.

1. 모델 간 오탐률 차이보다 **정답지 자체의 흔들림**이 생각보다 컸다.
2. 실제 차이는 정확도보다 **커버리지**에서 더 선명하게 나타났다.
3. 좁은 태스크에서는 최고급 모델보다 **저가형 모델이 비용 대비 훨씬 좋은 선택**이 될 수 있었다.

---

# 평가 조건

같은 2,000개 입력을 6개 모델에 넣고, 후처리 없이 모델이 처음 생성한 결과만 비교했다.

비교한 모델은 다음과 같다.

```text
GPT-5.6 Luna
Claude Opus 5
Claude Sonnet 5
Claude Haiku 4.5
Gemini 3 Pro
Claude Sonnet 4.6
```

평가에서 가장 중요하게 본 지표는 **오탐률**이었다.

검색 키워드 생성에서는 키워드를 많이 뽑는 것도 중요하지만, 관련 없는 키워드가 섞이면 오히려 검색 품질을 망칠 수 있기 때문이다.

그래서 단순 정확도 하나만 보는 대신 다음 지표를 같이 봤다.

```text
오탐률
커버리지
건당 키워드 수
빈 결과 비율
비용
재현성
```

그리고 모델이 만든 정답지에 평가가 종속되는 문제를 줄이기 위해 서로 독립적으로 만든 **두 벌의 정답지**로 각각 점수를 냈다.

---

# 결과 1. Luna와 Opus 5의 오탐률은 사실상 구별하기 어려웠다

독립 정답지를 기준으로 본 결과는 다음과 같았다.

| 모델 | 건당 키워드 | 빈 배열 | 상품 단위 오탐률 하한 | 커버리지 |
|---|---:|---:|---:|---:|
| **GPT-5.6 Luna** | 2.21 | 45 | **2.60%** | 81.52% |
| **Opus 5** | 2.43 | 28 | 3.25% | **91.24%** |
| Sonnet 5 | 0.95 | 527 | 2.15% | 37.23% |
| Haiku 4.5 | 1.26 | 193 | 8.30% | 44.88% |
| Gemini 3 Pro | 6.09 | 1 | 13.40% | 85.52% |
| Sonnet 4.6 | 3.27 | 14 | 14.75% | 83.02% |

표만 보면 Luna의 오탐률이 Opus 5보다 낮다.

하지만 다른 정답지를 사용하면 순서가 바뀌었다.

| 모델 | 다른 정답지 기준 오탐률 하한 | 커버리지 |
|---|---:|---:|
| GPT-5.6 Luna | 4.30% | 74.84% |
| Opus 5 | 3.85% | 85.80% |
| Sonnet 5 | 4.50% | 33.11% |
| Haiku 4.5 | 10.20% | 42.24% |
| Gemini 3 Pro | 17.30% | 85.90% |
| Sonnet 4.6 | 17.20% | 82.55% |

즉 정답지를 누가 만들었느냐에 따라

```text
정답지 A
Opus 5 < Luna

정답지 B
Luna < Opus 5
```

처럼 앞뒤가 바뀌었다.

Luna와 Opus 5 사이의 차이에 대해 McNemar 검정을 적용했을 때도 `p ≈ 0.093` 수준이었다.

일반적으로 사용하는 0.05 기준에서는 **두 모델의 오탐률 차이가 통계적으로 명확하다고 말하기 어렵다.**

이 결과에서 내가 받은 인상은

> Luna가 Opus를 이겼다

가 아니라

> 이 태스크에서는 Luna와 Opus의 오탐률 차이를 현재 평가 방법으로 구분하기 어렵다

에 가깝다.

---

# 결과 2. 실제 차이는 커버리지였다

오탐률보다 훨씬 뚜렷하게 차이가 난 것은 **커버리지**였다.

독립 정답지를 기준으로 보면:

```text
Opus 5       91.24%
Gemini       85.52%
Sonnet 4.6   83.02%
Luna         81.52%
Haiku 4.5    44.88%
Sonnet 5     37.23%
```

Opus 5와 Luna의 차이는 약 **9.7%p**였다.

정답지를 바꿔도 이 차이는 유지됐다.

그래서 두 모델을 비교할 때는

```text
오탐률 → 거의 비슷
커버리지 → Opus 5 우위
```

라고 보는 것이 더 정확했다.

이 차이는 실제 운영에서는 꽤 중요할 수 있다.

오탐이 절대적으로 중요한 시스템이라면 Luna가 굉장히 매력적이고,

놓치는 키워드를 최대한 줄여야 한다면 Opus의 높은 커버리지가 의미가 있다.

결국 모델 선택은 단순 순위가 아니라 **어떤 오류를 더 싫어하느냐**의 문제다.

---

# Sonnet 5의 낮은 오탐률은 함정이었다

표에서 또 하나 눈에 띄는 모델이 Sonnet 5다.

오탐률만 보면 **2.15%**로 가장 낮다.

하지만 2,000건 중 **527건에서 아무 키워드도 생성하지 않았다.**

커버리지는 37.23%였다.

```text
아무것도 안 내면
틀릴 가능성도 줄어든다.
```

그래서 이런 태스크에서는 오탐률만 단독으로 보면 안 된다.

```text
Precision만 보면 좋아 보임
        │
        ▼
하지만 Recall / Coverage가 너무 낮음
```

오탐률과 커버리지를 항상 같이 봐야 하는 이유다.

---

# Gemini와 Sonnet 4.6은 많이 뽑지만 오탐이 컸다

Gemini 3 Pro는 건당 평균 **6.09개**의 키워드를 생성했다.

Luna의 약 2.8배다.

커버리지도 85% 이상으로 높았다.

문제는 오탐률이었다.

```text
Gemini 3 Pro   13.40%
Sonnet 4.6     14.75%
```

이번 태스크에서는 오탐이 가장 중요한 지표였기 때문에 높은 커버리지만으로 이 단점을 상쇄하기 어려웠다.

이 결과도 재미있었다.

**더 많은 답을 생성하는 모델이 반드시 더 좋은 모델은 아니었다.**

특히 검색, 추천, 자동 태깅처럼 잘못된 결과가 downstream 품질에 영향을 주는 시스템에서는 보수적인 모델이 더 좋은 선택이 될 수 있다.

---

# 결과 3. 가장 놀라웠던 것은 비용이었다

Luna가 흥미로웠던 가장 큰 이유는 사실 정확도보다 비용이었다.

Amazon Bedrock의 GPT-5.6 Luna 공식 가격은 짧은 컨텍스트 기준 100만 토큰당:

```text
Input        $0.22
Cache Read   $0.022
Output       $1.32
```

이다.

동일한 워크로드 형태와 캐시 사용을 가정하고, **맞힌 키워드 1,000개를 얻는 데 필요한 비용**으로 정규화해 비교해봤다.

| 모델 | 맞힌 키워드 1,000개당 추정 비용 | Luna 대비 |
|---|---:|---:|
| **GPT-5.6 Luna** | **$0.54** | **1.0x** |
| Haiku 4.5 | $3.81 | 7.1x |
| Gemini 3 Pro* | $4.46 | 8.3x |
| Sonnet 4.6 | $6.69 | 12.4x |
| Sonnet 5** | 약 $10.42 | 19.3x |
| Opus 5 | $11.29 | 20.9x |

\* Gemini 비용은 비교 당시 사용한 가격 가정을 기준으로 한 추정치다.

\** Sonnet 5는 2026년 8월 가격이 `$2 / $10`으로 최종 확정되어, 이전 `$3 / $15` 기준 계산값을 현재 가격에 맞춰 보정했다.

여기서 중요한 것은

> 최신 frontier 모델이 싸고 좋았다

가 아니다.

Luna는 GPT-5.6 계열에서도 **비용 효율을 노린 저가 티어**다.

그런 모델이 특정한 좁은 태스크에서 Opus 5와 구별하기 힘든 오탐률을 보여줬다는 점이 흥미로운 것이다.

LLM을 대량으로 호출하는 서비스에서는 이런 차이가 굉장히 커진다.

```text
모델 성능 2% 향상
        vs
호출 비용 20배 증가
```

둘 중 어느 쪽이 더 중요한지는 워크로드에 따라 완전히 달라진다.

---

# 재현성도 확인해봤다

LLM 평가에서 한 번 잘 나온 결과만 보고 결론을 내리는 것도 위험하다.

그래서 Luna를 동일한 표본으로 세 번 실행했다.

| Run | 건당 키워드 | 오탐률 하한 | 커버리지 |
|---|---:|---:|---:|
| r1 | 2.21 | 4.30% | 74.84% |
| r2 | 2.21 | 3.90% | 74.86% |
| r3 | 2.22 | 4.10% | 75.44% |

집계 지표는 상당히 안정적이었다.

```text
건당 키워드 폭   0.01
오탐률 폭        0.40%p
커버리지 폭      0.60%p
```

그런데 개별 결과를 보면 이야기가 달랐다.

같은 입력에서 세 실행이 **완전히 같은 키워드를 생성한 비율은 약 55%**였다.

Jaccard 유사도는 약 75% 수준이었다.

즉,

```text
전체 통계는 안정적
개별 출력은 꽤 흔들림
```

이라는 특징이 있었다.

이건 생성형 모델을 실제 시스템에 넣을 때 꽤 중요한 포인트다.

평균 성능만 보면 안정적이어도 특정 입력에서는 매 실행마다 다른 결과가 나올 수 있다.

---

# 더 어려운 문제는 정답지도 흔들린다는 것

이번 테스트에서 개인적으로 가장 인상 깊었던 부분이다.

같은 2,000개 입력을 서로 독립적으로 두 번 라벨링한 결과를 비교해보니:

```text
정답 완전 일치     46.4%
Jaccard             69.4%
직접 충돌            3.4%
```

였다.

절반 이상에서 정답 목록이 완전히 같지 않았다.

다만 대부분은

```text
A는 키워드 3개
B는 키워드 2개
```

처럼 한쪽이 조금 더 넓게 인정하는 차이였고,

한쪽에서는 정답인데 다른 쪽에서는 명확한 오답으로 보는 **직접 충돌은 3.4%**였다.

이걸 보고 나니 1~2%p 정도의 모델 차이를 너무 진지하게 해석하면 안 되겠다는 생각이 들었다.

```text
모델 차이     0.5%p
정답지 흔들림 1~3%p
```

이라면 모델을 평가하는 자 자체가 모델 간 차이보다 더 크게 흔들릴 수도 있기 때문이다.

그래서 Luna와 Opus 5의 미세한 차이를 정말 가르고 싶다면 결국 **사람이 직접 맹검 평가하는 과정**이 필요하다.

---

# 이번 비교에서 얻은 결론

이번 결과를 한 문장으로 줄이면 이렇게 정리할 수 있을 것 같다.

> **좁고 반복적인 LLM 태스크에서는 가장 비싼 모델보다, 충분히 정확한 저가 모델을 찾는 것이 훨씬 중요할 수 있다.**

이번 검색 키워드 생성 태스크에서는:

```text
오탐률
Luna ≈ Opus 5

커버리지
Opus 5 > Luna

비용 효율
Luna >>> Opus 5
```

였다.

그래서 오탐을 낮게 유지하면서 대량 처리가 필요한 상황이라면 Luna가 굉장히 매력적인 선택지로 보였다.

반대로 높은 커버리지가 반드시 필요한 구간이라면 Opus 5를 사용할 이유도 충분히 있다.

오히려 다음 단계로 재미있어 보이는 것은 **한 모델만 사용하는 구조가 아니다.**

```text
일반 케이스
   │
   ▼
 Luna
   │
   ├── confidence 충분 → 결과 사용
   │
   └── 애매한 케이스
             │
             ▼
           Opus 5
```

대부분의 입력은 저렴한 모델로 처리하고,

Luna와 Opus의 커버리지 차이가 크게 발생하는 특정 구간만 비싼 모델에 보내는 방식이다.

LLM 비용 최적화도 결국 전통적인 시스템 설계와 비슷해지는 것 같다.

**모든 요청에 가장 비싼 컴퓨팅 자원을 쓰는 대신, 필요한 곳에만 비싼 자원을 사용한다.**

앞으로 LLM을 제품에 넣을 때도 "어떤 모델이 제일 좋은가?"보다

> 이 태스크에서 필요한 품질 수준은 어디까지이고, 그 품질을 가장 싸게 만족하는 모델은 무엇인가?

를 먼저 물어보게 될 것 같다.
